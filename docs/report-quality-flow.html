보고서는 어떻게 최종 확정되는가

PDF가 만들어져도 바로 최종 보고서가 되지는 않습니다. 생성된 본문과 PDF를 검사하고, 독립 LLM이 내용의 품질을 평가한 뒤 모든 조건을 통과한 버전만 확정합니다.

품질 미달 → 같은 기업의 문제 블록만 수정 → 재평가
기존 분석·투자 점수·판정은 유지합니다. 품질 루프에서 다음 기업을 선택하거나 조사를 다시 실행하지 않습니다.

실제로 실행한 E2E 테스트 흐름

Judge 기준 조정: 코드로 확정한 점수·판정·평가 이력은 State와 대조합니다. 정보 부족·추가 실사 필요 같은 정직한 유보 표현을 허용하고, 명확한 근거 위반·무조건 추천·한계를 숨긴 단정이 있을 때 미달로 판정합니다. 수치·인용·분량·확정 판정의 코드 검사와 3개 품질 항목은 유지합니다.

전체 그래프의 실제 실행 기록을 확인합니다.

변경 전 실행은 원문에 없는 1.3·2.6 수치 때문에 PDF 생성 전에 종료됐습니다. 이번 실행은 블록 수정·대체 후 PDF와 독립 Judge 평가까지 도달했습니다. 실제 모델 응답과 평가 기업이 달라 동일 입력의 A/B 비교는 아닙니다. 반복 수치 제거와 정상 블록 보존은 별도 회귀 테스트로 검증했습니다.

      개선할 때는 무엇이 실제로 바뀌나요?

      평가 결과를 다음 생성 요청에 넣고 정상 블록은 유지하고 문제 블록만 수정한 뒤 SUMMARY를 재생성합니다. 이전 블록 원문과 실패 위치를 전달합니다. 수정 후에도 검증에 실패하면 코드가 해당 블록의 주장을 정보 부족 표시로 대체합니다.

      1. 실패 위치 저장장·블록·원문·수치·출처
        issues / repair_log
      2. 문제 블록만 요청기존 블록 + 실패 이유
        + 분석·원문 발췌
      3. 재검증 후 대체1회 수정 → 재검증
        실패한 주장은 코드로 제외
      4. SUMMARY·PDF·평가수정된 본문으로 요약
        품질 기준 그대로 재평가

      코드에서는 이전 보고서를 어떻게 비교·수정하나요?

      이전 draft_vN.json의 보고서와 quality_result.issues를 읽습니다. 해당 장·블록 위치만 수정 대상으로 선택하고 나머지 블록은 그대로 복사합니다.

      request = {
  "operation": "repair_block",
  "previous_block": 실패한_블록_원문,
  "violations": 장_블록_문장_수치_출처_실패이유,
  "inputs": 기존_분석,
  "evidence": 기존_원문_발췌,
  "quality_feedback": 이전_평가결과
}
# 블록 1개만 수정 → 동일 수치·출처·분량 검사
# 재실패: 코드가 정보 부족 블록으로 대체
# 정상 블록은 유지 → SUMMARY 재생성 → PDF → 품질 평가

      이제 이전 블록 원문을 직접 제공합니다. repair_log에 수정 전·후와 실패 원인을 보존하며, SUMMARY 생성에도 이전 요약을 제공합니다. SUMMARY에 새로 등장한 근거 없는 수치도 같은 원칙으로 거부합니다.

      agents/report_writer.py · block_issues() · _repair_block() · _previous_report() · build_report()

      LLM 수정 결과를 코드로 재검증합니다. 수치·인용·분량 검증에 재실패하면 해당 블록을 코드로 대체합니다. 의미·범위·편향의 품질 기준은 독립 Judge로 계속 검사합니다.

      근거를 새로 찾지는 않습니다. 기존 자료가 부족하면 주장 삭제·유보·정보 부족 표시로 개선하며, 같은 문제가 남으면 v3에서 최종 보고서 없이 종료합니다. 품질 루프에 들어갔다고 자동으로 글자 예산을 줄이지는 않습니다. 분량 축소는 장별 검증 실패나 PDF 5쪽 초과 처리에서 별도로 작동합니다.

      무엇을 개선하고, 무엇을 유지하나요?

      다시 생성하는 것

      • 문제가 있는 블록만 LLM으로 수정하고 SUMMARY를 새로 생성합니다.
      • 이전 quality_result.issues의 위치·실패 문장·수치·출처를 해당 블록 수정 입력으로 전달합니다.
      • 재검증에도 실패한 블록은 정보 부족으로 대체하며, 점수·판정·코드 표는 변경하지 않습니다.

      그대로 사용하는 것

      • 선택된 기업과 기존 기술·시장·경쟁 분석
      • 투자 점수·판정·평가 이력과 코드 생성 표
      • 이미 수집한 원문 발췌와 출처

      이 루프에는 추가 검색·RAG·기업 교체가 없습니다. 필요한 근거가 애초에 없다면 문장을 고쳐도 통과가 어려울 수 있습니다.

      “다시 시도”가 세 종류라서 헷갈려요
      1. 한 블록 내부의 수정: 인용·수치·글자 수에 실패한 블록만 한 번 수정합니다. 재실패하면 해당 블록을 정보 부족으로 대체합니다. SUMMARY도 한 번 수정하고 재실패하면 확정 State를 사용한 제한된 요약으로 대체합니다. 이때 보고서 버전은 증가하지 않습니다.
      2. PDF 분량 축소: 5쪽을 넘으면 본문 예산을 100% → 80% → 64%로 줄여 다시 생성·조판합니다. 그래도 넘으면 압축 조판을 시도합니다. 이것도 같은 버전 내부의 처리입니다.
      3. 그래프의 품질 개선 루프: 평가 후 미달이면 이전 보고서를 읽어 실패 위치만 수정하고 새 버전을 만듭니다. 동일 블록이 다시 의미 평가에 실패하면 추가 LLM 수정 대신 정보 부족으로 대체합니다. 최초 v1 + 개선 v2·v3, 최대 3개 버전입니다.

      품질 Judge 호출·응답 검증은 최대 2회 시도합니다. 그래도 실패하면 통과로 처리하지 않고 개선 불가로 종료합니다. 인증·요청 설정 오류가 ConfigurationError로 전파되는 경우에는 그래프 실행 자체가 예외로 중단될 수 있습니다.

      어느 파일을 보면 실패 원인을 알 수 있나요?

      outputs/runs/{run_id}/ 안에서 같은 버전 번호를 비교하면 됩니다.

      생성 결과

      draft_vN.json
      생성된 보고서 또는 error_code·error_reason

      preview_vN.pdf / .md
      평가용 산출물. 생성 실패 시 PDF는 없을 수 있습니다.

      평가와 최종 결과

      quality_vN.json
      각 항목의 passed·reason·feedback, 구조 검사와 recoverable

      report_vN.pdf / .md
      통과한 버전만 생성하는 최종 산출물

      생성 오류를 기록한 평가 결과에서는 3개 내용 항목 모두 같은 오류로 실패할 수 있습니다. 실제로 LLM이 3개 항목을 각각 평가했다는 의미는 아닙니다.

      방금 수정한 평가 오탐은 어떻게 달라졌나요?

      원문에 숫자 7이 없어도 “현장 실증 근거로 TRL 7로 평가한다”는 분석 결과일 수 있습니다. 현재 코드는 투자 보고서 1장에서 State의 TRL 값·판단근거·기술 출처가 연결된 명시적 평가의 숫자 위치만 예외 처리합니다.

      State와 다른 TRL, 같은 문단의 근거 없는 “7 GW”, 출처 없는 평가는 계속 거부합니다. LLM Judge는 원문 발췌가 실제 판단근거를 지지하는지 별도로 검사합니다.

      전체 자동 테스트 290개가 통과했습니다. Judge 기준을 완화한 최신 실제 보고서 구간 검증은 v1에서 근거성·중립성·편향 및 구조 검사를 통과하여 최종 PDF가 확정됐습니다. 페이지 상단은 이번 실행, 시뮬레이션의 “이전 실제 실행 기록”은 수정 전 결과입니다.

      코드 기준: agents/report_writer.py · agents/report_quality.py · graph/routing.py · schemas.py · config.py
      단계를 클릭하면 내부 입력·출력·검사를 볼 수 있습니다. 상황 선택과 “다음 단계”는 설명용 재생이며 실제 모델이나 파일 생성 작업을 실행하지 않습니다.
